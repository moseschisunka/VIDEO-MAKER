# PR-307 — Fast preflight and deep diagnostics split

Status: **VERIFIED**

`lib/providers/preflight.py` adds a local-only `fast_preflight` with a short
TTL cache and the required status vocabulary: `configured`, `available_local`,
`degraded`, `unavailable`, `untested`, and `requires_live_probe`. It never
calls `get_status`, opens a socket, or performs npm/provider health checks.
`deep_preflight` is opt-in and bounds each live status call.

Measured on Windows 11 / Python 3.13.2 with 115 discovered tools:

```text
true cold fast preflight:       1320.09 ms
30 warm fast-preflight p95:      258.96 ms (max 269.02 ms)
10 provider-menu-summary p95:    715.08 ms (max 712.77 ms)
```

Evidence:

```text
python -m pytest -q tests/contracts/test_phase3_preflight.py
3 passed
python -m pytest -q tests/tools/test_hyperframes_compose.py::test_provider_menu_summary_returns_expected_shape tests/tools/test_hyperframes_compose.py::test_provider_menu_summary_deduplicates_providers_across_buckets
2 passed
```

The result meets the roadmap's warm-under-2-second and cold-under-5-second
targets in this reference environment. Deep live probe duration remains
separately observable and is not part of Studio-open latency.
