# PR-1014 — Derive library completion metrics from truthful project state

Status: **VERIFIED (local source/test and read-only browser evidence; supported
CI rerun pending)**

## Finding

After PR-1013 made card progress manifest-aware, the library aggregate metric
and its “Rendered Outputs” filter still used the legacy hard-coded
`completed_count >= 5` threshold. A seven-stage project could therefore be
treated as complete at five stages, while a project with a real render but an
incomplete checkpoint rail could be excluded from the aggregate.

The defect was found by source review against the Phase 10 precision contract
at source checkpoint `6b59d8e` (the PR-1013 documentation checkpoint).

## Implementation

- Added `projectIsComplete(project)` as the one completion predicate used by
  both the aggregate metrics and the completed filter.
- Preserve a verified rendered output (`render_count > 0`) as an output even
  when its stage rail is not fully complete.
- Use the manifest-derived `projectProgress(project)` result for projects with
  no rendered output, removing the hard-coded five-stage assumption.
- Added static release-blocking assertions that both consumers use the shared
  predicate and that `completed_count >= 5` is absent.

Implementation checkpoint: commit `58439f9` (`fix(ui): derive completion
filters from project state`).
