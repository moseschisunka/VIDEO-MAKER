# PR-1021 — Reject malformed provider approval flags

Status: `IMPLEMENTED` locally; supported CI verification remains required.

## Finding

The shared provider bridge, request contract, and ranked dry-run plan used
Python truthiness for the spend-approval flag. Values such as `"false"`, `1`,
or `None` could therefore be serialized as approval and allow a paid stock,
image, video, music, or voice provider path to appear ready. The defect was
especially dangerous because normal boolean fixtures remained green.

## Remediation

- Added a shared `strict_bool()` provider-boundary helper that accepts only a
  real boolean and raises a structured contract error for every other value.
- Enforced the type in `ProviderRequest` before serialization or execution.
- Made the provider bridge fail before the implementation callable when either
  `provider_approved` or `approved` is malformed, while preserving the
  explicit `provider_approved` precedence rule.
- Made ranked selector plans remain dry-run/no-spend and report
  `blocked_invalid_approval` plus `approval_error` instead of coercing a bad
  value into consent.
- Added regression coverage for direct requests, bridge execution, both
  approval aliases, and malformed string/integer/null values.

## Residual scope

This closes malformed approval coercion at the common provider execution and
planning boundary. It does not prove live provider authorization, external
metrics/paging delivery, trusted-edge enforcement, deployment rollback, human
audiovisual review, frozen release-candidate certification, or `PR-11G`.

## Rollback

Revert the PR-1021 code and regression tests together only after preserving
this finding. Do not restore truthy approval coercion in a production release.
