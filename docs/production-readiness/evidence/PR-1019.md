# PR-1019 — Scrape-compatible metrics export

Status: `IMPLEMENTED` locally; external sink, durable retention, and supported
CI verification remain open under `OBS-02`/`PR-10G`.

## Finding

Backlot exposed only a JSON in-process metrics snapshot. An operator could
inspect it manually, but a standard metrics scraper needed a deployment-owned
adapter, which increased configuration drift at the trusted edge. The local
registry also contains bounded latency summaries rather than Prometheus
histogram buckets; silently labelling those values as buckets would be
misleading.

## Remediation

- Added `MetricsRegistry.prometheus_text()` with deterministic metric types,
  label-name/value escaping, and explicit summary output (`quantile=0.5`,
  `quantile=0.95`, `_count`, `_sum`). No buckets are fabricated.
- Added authenticated `GET /api/metrics/prometheus` with
  `text/plain; version=0.0.4` and `Cache-Control: no-store`.
- Retained `GET /api/metrics` as the JSON diagnostic contract.
- Declared the scrape endpoint and format in `config/observability.yaml` and
  documented the deployment requirements in `docs/operations/OBSERVABILITY.md`.

## Residual scope

This makes the service scrape-ready but does not prove an external metrics/log
aggregator, durable monthly SLO denominators, alert delivery, trusted-edge
enforcement, or deployment rollback. `OBS-02`, `OBS-03`, `SEC-06`, `REC-03`,
`PR-10G`, and `PR-11G` remain open/blocked as recorded in the tracker.

## Rollback

Revert the PR-1019 commit to remove the additional route/exporter while
retaining the JSON metrics endpoint. No project artifacts or user media are
modified by this change.
