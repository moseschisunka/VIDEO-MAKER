# PR-201 — Run record and output provenance

**Date:** 2026-09-02
**Task status:** `VERIFIED`
**Owner:** OpenMontage execution agent
**Depends on:** `PR-1G` (`COMPLETE`)
**Next task:** `PR-202` — make `/run` idempotent

## Goal

Ensure each accepted run has one durable identity and that every checkpoint,
canonical stage artifact, tool result, and local output can be traced to the
project, pipeline, run, attempt, producing stage, and producing tool.

## Implementation

- Added the versioned `schemas/runs/run_record.schema.json` contract and the
  atomic, locked `lib/run_record.py` store under
  `projects/<project-id>/runs/<run-id>/run.json`.
- Work-order creation and all lease/state mutations create or synchronize the
  matching run record without inventing a new run or attempt.
- Checkpoints now carry `attempt`, `producer_stage`, and `producer_tool`.
- Manifest stage submissions accept `producing_tool`, persist it in the
  checkpoint, and register each submitted artifact plus the checkpoint in the
  run record with path, hash, size, and timestamps.
- BaseTool instrumentation enriches events with stage/agent identity and adds
  a validated `data.provenance` object to project-backed results while
  registering local result/output paths. Telemetry remains non-fatal to tool
  execution.
- Event writes no longer mutate caller payloads and derive missing attempt and
  active-stage values from the durable work order.
- Render reports accept the same producer/provenance fields, preserving the
  existing runtime and output contract.

## Residual risks

Run records currently index local paths and hashes; atomic candidate promotion,
fresh-output proof, per-run staging, idempotent `/run`, and media-property
verification are deliberately deferred to `PR-202`–`PR-207`. Provider attempt,
cost, retry, and fallback provenance remains a Phase 3 responsibility. The
production lock remains `PR-11G`.

## Rollback

Revert the run-record schema/module and the narrowly scoped integration hooks
as one reviewed change. Preserve existing work orders and checkpoints; older
projects remain readable because the new fields are optional at their schemas'
boundaries.
