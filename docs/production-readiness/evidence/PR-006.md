# PR-006 — Release-blocker CI semantics evidence

**Date:** 2026-09-02
**Task status:** `VERIFIED`
**Owner:** OpenMontage execution agent
**Depends on:** `PR-001` (`VERIFIED`)
**Scope:** CI and pytest policy only; no provider calls or production behavior changes

## Implemented controls

1. `pytest.ini` enables strict marker validation and declares the release-gate markers:
   `release_blocker`, `live_provider`, and `hyperframes_qa`.
2. `tests/conftest.py` marks every test under `tests/contracts` as
   `release_blocker` during collection. It also makes `live_provider` tests fail closed
   (skipped) unless `--run-live-provider` is explicitly supplied.
3. The optional Kling documentation snapshot check is marked `live_provider`.
4. HyperFrames QA is marked `hyperframes_qa` and remains separately controlled by its
   existing `HYPERFRAMES_QA`/`HYPERFRAMES_QA_RENDER` environment gates.
5. `Makefile` exposes the same local `test-release-blockers` and `test-offline`
   commands used by the CI policy.
6. `.github/workflows/ci.yml` now has four explicit jobs:
   - `release-blockers`: offline contract surface; any contract failure fails CI;
   - `offline-regression`: deterministic suite excluding live-provider and HyperFrames QA;
   - `live-provider`: workflow-dispatch only, with explicit `run_live_provider` approval;
   - `hyperframes`: workflow-dispatch only, with explicit `run_hyperframes` approval.

Push and pull-request events run only the release-blocking and deterministic offline jobs.
Potentially paid, networked, or resource-heavy checks cannot run accidentally on a normal
push or pull request.

The local targets and CI commands use the same marker expressions, so a developer can
reproduce the gate without relying on a different test selection implementation.

## Verification results

### Collection and marker policy

Command:

```text
python -m pytest tests/contracts --collect-only -q -m "release_blocker and not live_provider and not hyperframes_qa"
```

Result: **761 of 762 tests selected; 1 live-provider test deselected**. Strict marker
validation passed.

Default live-provider behavior:

```text
python -m pytest tests/contracts/test_kling_official_core.py -q
23 passed, 1 skipped
```

Explicit live-provider selection without the opt-in environment remains non-networked and
skips the live documentation check:

```text
python -m pytest tests/contracts/test_kling_official_core.py -m live_provider --run-live-provider -q
1 skipped, 23 deselected
```

Default HyperFrames QA behavior:

```text
python -m pytest tests/qa/test_09_hyperframes_compose.py -q
2 skipped
```

### Release-blocker job

Command:

```text
python -m pytest tests/contracts -m "release_blocker and not live_provider and not hyperframes_qa" -q
```

Result: **754 passed, 1 failed, 6 skipped, 1 deselected in 225.15 seconds**.

The single failure is the pre-existing provider catalog expectation drift in
`tests/contracts/test_phase3_contracts.py::TestCapabilityMetadata::test_registry_catalog_views`.
This is the known `PR-300`/`PR-306`/`PR-309` blocker documented in `PR-000`; the new CI
semantics correctly make it a release-blocking failure. The test was not weakened and no
provider was contacted.

### Workflow structure

The workflow YAML parses successfully and exposes jobs:
`release-blockers`, `offline-regression`, `live-provider`, and `hyperframes`. The latter two
are conditional on `workflow_dispatch` boolean inputs and therefore do not run on ordinary
push/pull-request events.

The Windows verification shell does not have GNU `make` installed, so the new Makefile
targets were syntax-inspected and their underlying pytest commands were run directly. CI
uses the same command expressions and will exercise the targets on its Linux runner.

## Acceptance decision

`PR-006` is verified because the release-blocker surface fails on a known contract defect,
while live-provider and HyperFrames work is opt-in and default test execution remains
deterministic. The red contract result is evidence that CI is enforcing the rule, not a
release waiver. `PR-0G` remains open until the existing blockers, golden scenarios, baseline
evidence, non-production labeling, and the human launch-scope decision are complete.

Production remains ineligible until every roadmap gate through `PR-11G` passes.
